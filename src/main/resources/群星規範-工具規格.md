# 群星規範——工具規格

工具規格最後修改：2026-10-08T01:05:48

*`ToolRunner.java` 與 `NewPaper.java` 的規格：各步驟的職責、validate 的檢查方式、關係的抽取與分類。讀者是作者與修改工具的 AI。任務 AI 與稽核 AI 不讀此文件。*

---

## 一、分工原則

**腳本只驗收，不生產。** 能機械判定的約束一律交給工具，讓 AI 的注意力集中在真正需要語意判斷的地方。約束本身的條文與「檢查者」在《稽核總表》；本文件只記錄工具**怎麼**檢查。

例外只有第 0 步的兩件事：label 為中文論文寫入句碼標籤，只加、換、刪標籤，不動其他任何字元（2.3）；stamp 只改時間戳那一行（2.1）。

---

## 二、執行步驟

在 IDE 中執行 `ToolRunner.main`，依序跑完第 0 到第 8 步。

| 步驟 | 輸出 | 職責 |
|---|---|---|
| 0. label、stamp | 中文論文的句碼標籤；更新暫存檔案的時間戳 | 先 label（2.3）：依正文內容寫入句碼標籤；再 stamp（2.1）：論文與概念表的 `last-modified`、手冊類文件開頭的「最後修改」 |
| 1. validate | 主控台報告 | 稽核總表中檢查者以「工具」開頭的條目（第三節），含與最後一次 commit 的版本比對（3.9） |
| 2. bundle | 論文資料夾中的 `形式化輸入包.md`、`稽核輸入包-甲.md`、`稽核輸入包-乙.md`、`稽核輸入包-形35.md` | 形式化與稽核任務的輸入包（第五節） |
| 3. tree | `PaperTree.html` | 論文引用關係圖 |
| 4. starmap | `starmap.html` | 概念星圖：節點取自概念表（public 較亮），邊取自抽取出的關係 |
| 5. concepts | `exports/concepts.jsonl` | 概念資料集，一行一個概念，關係依第四節抽取並分類 |
| 6. papers | `exports/papers.jsonl` | 論文全文資料集，一行一篇 |
| 7. checkPapers | 主控台報告 | 檢查 `papers.jsonl` 結構與交叉一致性 |
| 8. checkHf | 主控台報告 | 遠端確認 HF 資料集狀態；`HF_DATASET` 留空時略過 |

**validate 有「不通過」時，稽核輸入包與第 3 步以後的輸出中止；形式化輸入包仍以本輪現行材料重建。**「警告」不阻擋流程，但要人工確認。

形式化輸入包是產製形式化文件的工作材料，不代表 validate 已通過，因此不以 validate 成敗作為產生條件。每次執行仍先清除舊包；若 validate 不通過，只重建 `形式化輸入包.md`，不產生稽核分包，也不執行 tree、starmap 與資料集匯出。這可避免舊形式化包被清除後消失，也避免留下與現行正文、概念表或句碼不同步的過期包。

### 2.1 stamp

- 只處理 Git 暫存區中新增、修改、更名、複製的 `.md` 檔
- 檔案以 `---` 開頭者，更新 YAML 頭部的 `last-modified:`；否則在前十行內尋找 `某某最後修改：時間戳` 並更新
- 只改時間戳那一行，改完重新暫存。論文中的注釋保留在原始檔中，不受影響
- 同時有已暫存與未暫存修改的檔案一律跳過並提醒，以免把刻意不提交的修改一併暫存
- 不處理 `形式化輸入包.md`、所有 `稽核輸入包-*.md`，以及相容清理用的舊檔 `稽核輸入包.md`（皆為生成物）
- 不做任何連鎖更新。形式化文件頭沒有時間戳
- 找不到 git 或專案不是 Git 倉庫時略過

時間戳由工具填寫，是因為只有在作者的電腦上執行的程式，才拿得到正確的時間；AI 所在環境的時鐘不一定可靠。

### 2.2 NewPaper

產生 UUID v4，建立 `paper_UUID` 資料夾（`-` 換 `_`）與四個檔案：

- `中文標題.md`、`English Title.md`：YAML 頭部（`uuid`、`last-modified`）與佔位符一級標題
- `concepts.md`：YAML 頭部、「不登記」與「待決項」區塊，內容皆為「無」
- `formalization.md`：兩行文件頭（`論文：《中文標題》`、`UUID：……`）、「記號約定」與「待決項」段落

資料夾已存在時不建立任何檔案。時間戳取自本機時鐘。

### 2.3 label

為每篇論文的中文論文寫入句碼標籤（稽核總表 8.12）。英文翻譯、概念表、形式化文件、外部存根不處理。label 在 stamp 之前執行。

**單位切分。** 去掉 YAML 頭部與注釋（3.8）之後：

- **標題單位**：以 `##` 到 `######` 開頭的行，一行一個。一級標題不切
- **形式段單位**：一個程式碼區塊一個
- **文句單位**：其餘的非空行，但不含水平線 `---` 與只由 HTML 標籤構成的行。每行從頭掃描，遇到「。」「！」「？」即為一個單位的結尾；位於「」『』（）〔〕[] 之內者不切；句末標點之後緊接的右引號、右括號，以及強調標記的結尾 `*`、`_`，歸前一個單位。一行結尾若還有不以句末標點結束的文字，到行尾為一個單位。單位不跨行。去掉連結網址後沒有任何文字或數字的片段（只有標點、空白、Markdown 標記），不成為單位

**正規化。** 去掉既有的句碼標籤；連結 `[顯示文字](目標)` 換成顯示文字；標題單位去掉開頭的 `#` 與其後空白；去掉全部空白字元（含換行）。形式段單位取開頭行與結束行之間的內容，不含開頭行的語言標記。

**句碼。** 正規化後的文字以 UTF-8 編碼，取 SHA-256 摘要的前八個位元組，視為大端序的無號整數，除以 10 的 10 次方取餘數，左側補零成十位數字。

**相同與相撞。** 正規化文字相同的單位，句碼相同，允許。正規化文字不同而句碼相同時，依文件順序，後出現者在正規化文字之後接上「＃2」重算；仍相撞時改接「＃3」，依此類推。兩種情形在檔案被寫入時列於報告，屬資訊，不算不通過。

**標籤。** 寫作 `<!--句` 加十位數字加 `-->`，比對式為程式常數 `SENT_TAG`：

- 文句單位：緊接在單位最後一個字元之後
- 標題單位：行尾
- 表格列（以 `|` 開頭並結尾的行）中的行尾單位：放在最後一個 `|` 之前，以免多出一欄
- 形式段單位：獨立成行，緊接在程式碼區塊結束行的下一行。程式碼區塊內的註解會被顯示成文字，所以標籤不能放進區塊內

**寫回。**

- 先移除檔案中所有句碼標籤，包括位置錯誤者（注釋內、程式碼區塊內、一級標題上）與格式錯誤的變體（以 `<!--` 開頭、含「句」、但不符合 `SENT_TAG` 者），再依上述規則重新寫入
- 重新寫入的結果與原檔逐字相同時，不寫檔
- 寫入前後，去掉全部句碼標籤的內容必須逐字相同；不同即中止並報錯，不寫檔。這保證 label 只動標籤
- 寫檔後，若該檔在執行前已在 Git 暫存區中，重新暫存，讓 stamp 照常處理
- 同時有已暫存與未暫存修改的檔案跳過並提醒，理由同 stamp
- 只有句碼標籤的變動不改正文內容，不屬於勘誤（稽核總表 0.7）

## 三、validate 的檢查方式

Issue 代碼即稽核總表的編號。以下只列需要說明的條目；未列者是字面上的格式比對。

### 3.1 檔案辨識

- 論文資料夾：`src/main/java/paper_*`；外部存根：`src/main/java/ext/ext_*`
- 論文資料夾中，`concepts.md`、`formalization.md`、`形式化輸入包.md`、所有 `稽核輸入包-*.md`、相容清理用的舊檔 `稽核輸入包.md`、`README.md` 以外的 `.md` 是論文檔。檔名過半為 ASCII 字元者視為英文翻譯，否則為中文論文
- 論文標題取自 `formalization.md` 的 `論文：《……》` 行；沒有時取中文檔名
- 論文檔一讀入就先處理注釋（3.8）與句碼標籤（3.10）。之後的所有檢查，作用的都是注釋已以空行取代、句碼標籤已去掉的版本

### 3.2 正文與連結（論、譯、跨-01、跨-02、跨-17～跨-19、跨-22）

- **英文翻譯尚未開始**：英文檔的檔名仍為 `English Title`，且 YAML 頭部之後只有 `# English Title`（原封未動的模板）時，跳過「譯」組與跨-19，報告另印一行提示。檔名是佔位符但已有內容時，照常檢查並報譯-01。這讓形式化階段（翻譯還沒做）能通過 validate、取得輸入包
- **正文範圍**：去掉 YAML 頭部；程式碼區塊（以 ` ``` ` 開頭的行之間）與注釋（3.8）以空行取代，保留行號
- **連結**：以 `[顯示文字](目標)` 比對。目標依序比對本篇、外部存根、上游三種格式，都不符者報論-07／譯-03
- 以 `#` 開頭的行（各級標題）中的連結，報論-11／譯-04
- 錨點為 `new` 時：有上游目錄者報論-12（工具部分），否則報論-13；英文版一律報譯-03
- 顯示文字對應 ID 以「目錄 + ID」為鍵，同一顯示文字出現第二個鍵時報論-10／譯-05
- 上游連結：找不到資料夾、ID 不存在、已廢棄、非 `public`，皆報跨-22
- 本篇 ID 不存在於概念表時報跨-01；未廢棄條目未被連結時報跨-02（只算中文論文）
- 跨-19 比較中英文版合法連結（錨點符合 ID 格式者）的「目錄 + ID」集合

**跨-18：逐段對照。** 中英文各自分段後一一對照，由 `align`、`checkAlignment` 執行：

- 分段作用於 3.1 所說的版本（注釋以空行取代、句碼標籤已去掉），另外去掉 YAML 頭部，程式碼區塊以空行取代
- 空行與水平線 `---` 結束一段；每個標題（以 `#` 開頭的行）、每個清單項目（以 `-`、`*`、`+` 或「數字.」加空白開頭的行）各自成一段。表格、引文等其餘連續的非空行合為一段
- 先比對兩邊每一段的種類（正文，或第幾級標題）。從頭比到第一個種類不同的段落，或兩邊段數不同時，報跨-18：段落結構不一致，無法逐段對照。報告附兩邊的段數、第一個種類不同的位置，以及從頭比對時第一個連結目標不同的段落（多出或缺少的段落通常就在這附近）
- 結構一致時，逐段比較合法連結（錨點符合 ID 格式者）的「目錄 + ID」集合。集合不同的段落各報一條跨-18，附中英文行號與兩邊多出的 ID
- 只比集合，不比個數與次序：英文語序與中文不同，同一概念在一段中出現的次數也可能不同。連結落在段中哪個詞上，由跨-17 的顯示文字比對補足

**跨-17 警告：英文顯示文字。** 由 `checkEnDisplay` 執行，只看英文版的合法連結：

- 顯示文字與該 ID（本篇或上游）在概念表中的英文名，各自轉小寫、以空白與連字號切成詞
- 顯示文字中依序出現英文名的每一個詞，即通過；前後多出的詞視為限定詞。兩個詞相符，指：相同；去掉複數詞尾（`-s`、`-es`、`-ies`，以及 `-ves` 改回 `-f`）後相同；或共同字首至少 5 個字母，或至少 4 個字母且達較短者長度的六成（例如 selves 對 self、distinguished 對 distinction、occurs 對 occurrence）
- **簡寫**：顯示文字恰為英文名中連續的幾個詞（不是全部），而且中文對應段落中，有連到同一 ID、顯示文字不是概念表中文名的連結時，通過。這需要跨-18 的分段對得上；對不上時，簡寫一律列入警告
- 其餘不符者依「顯示文字 → 英文名」合併為一條警告，附出現次數與第一處行號。詞形規則是寬鬆的近似，警告只是線索：是否屬於容許的變化，由稽核判斷（例如 dead 對 Death）

**論-06 警告**：去掉程式碼區塊、注釋、YAML 頭部、標題行與所有連結之後，正文中若仍出現字面上等於本篇概念中文名的片段，逐一列為警告。從最長的概念名開始比對，比中的片段以占位字元取代，避免「信空間」再被「信」比中。

### 3.3 外文限制（論-14、論-15、概-22、形-13、形-14）

- 拉丁與希臘字母：`[A-Za-z]` 與 Unicode 希臘字母區段 `U+0370–U+03FF`
- 先去掉所有 `〔…〕` 片段，再掃描剩下的文字
- 中文論文另外去掉 YAML 頭部、連結網址、程式碼區塊開頭行的語言標記、注釋（3.8）
- 形式化文件另外去掉文件頭兩行、`UUID` 與 `ext:UUID`
- 概念表只檢查中文名
- 括號檢查：巢狀、不成對、空括號；只含單一字母時，前後至少一側須為漢字

工具只能判斷外文有沒有被標記，無法判斷該不該被標記，後者由稽核負責（論-16、概-23、形-15）。

### 3.4 概念表（概、存）

- **條目解析**：以獨立成行的 `<a id="……"></a>` 為起點，下一行須符合 `## 修飾子 中文名 / English Name`。下一行不是二級標題時報概-05；是二級標題但格式不符時報概-06
- 條目結束於下一個錨點或下一個 `## ` 行
- 概-08：出現「前一行不是錨點」的二級標題之後，又出現錨點
- **概-12（工具部分）、概-34**：掃描每個未廢棄條目的「- 定義：」與「- Definition: 」行中的連結，同一條目連到同一目標只報一次。格式不在三種之內、目標不存在或已廢棄、連到他篇的非 `public` 條目，報概-34；`public` 條目連到本篇的 `private` 條目，報概-12
- 概-14（工具部分）：定義含「如上」「前述」「上述」「本文第」任一字眼。字眼清單為程式常數 `CONTEXT_WORDS`
- 概-15 警告：定義去掉連結後，仍出現其他本篇概念中文名的片段
- 概-29、概-30：`## 待決項` 之後到下一個二級標題或檔尾，去掉空白後為「無」或空，即視為清零
- 概-33：`## 不登記` 須出現在 `## 待決項` 之前；區塊內每個非空行須為「無」，或符合 `- 名稱：YYYY-MM-DD 理由`
- 外部存根：不檢查待決項與不登記；檢查存-01、存-02、存-03、概-34，並參與版本比對（3.9）

### 3.5 形式化文件（形、跨-09、跨-23～跨-25、跨-28、跨-29）

- **文件頭**：第一行符合 `論文：《……》`，第二行符合 `UUID：` 加 36 字元 UUID。行數為程式常數 `F_HEADER_LINES = 2`，抽取與段落解析一律從第三行起算
- **段落**：以 `## ` 開頭的行切分。第一個段落須為「記號約定」（形-03）；「待決項」以外的段落，內容去掉前導空白後須以「來源：」開頭（形-04）；最後一個段落須為「待決項」（形-29）
- **跨-09**：「記號約定」段落的第一個非空行若以「來源：」開頭，必須恰為 `來源：論文全文`。其餘段落的「來源：」指向實際存在的章節，由形-38（引用的句碼中至少一個是標題單位）與跨-30（句碼存在）共同保證
- **上游概念**：以 `(ext:)?UUID.概念名` 比對，概念名到空白或 `，,、。；;（(）)：:「」` 為止。UUID 等於本篇者報形-06；在上游找不到同名條目報跨-23；非 `public` 報跨-24；論文正文沒有連到同一條目報跨-25
- **正文引用**：行尾的 `【正文：句十位數字、句十位數字……】`。句碼以「、」分隔，每個都以「句」開頭
- **形-08 切詞**：去掉上游概念識別與行尾的正文引用後，以空白與 `，。、；：:（）()「」《》〈〉【】[]-_+,/` 切分全文（程式碼區塊除外）。切出的片段若包含某個本篇概念中文名，就必須恰好等於某個概念名，或出現在「記號約定」段落切出的片段中。從最長的概念名開始比對
- **形-09**：程式碼區塊外出現 `→⇒↝≡⊕⊗⊂⊆⊥∈∉∨∧¬=≠≤≥×` 任一字元。清單為程式常數 `REL_SYMBOLS`
- **形-16（工具部分）**：含 `蘊含(` 的行，必須同一行有 `（從……推出`
- **形-22**：「前置條件」段落中，每行第一個全形冒號之前的部分，以 `前提` 加中文數字（一至十的組合）辨認前提編號；同一部分含 `[限定條件]` 者為限定條件。全文所有 `（從……推出` 的來源中出現過的前提編號，視為被引用。非限定條件且未被引用者報錯。因此前提的寫法必須是 `- 前提一：……` 或 `- 前提三 [限定條件]：……`，這是形式化手冊第三節規定固定寫法的原因
- **形-39**：「前置條件」段落中，以 `前提` 開頭的行（含限定條件），去掉行首的 `- ` 與行尾的正文引用後含「公理」二字者報錯
- **形-30**：同 3.4 節的清零判定
- **形-33（工具部分）**：推導來源中出現「待決項」三字
- **形-36**：推導行指行首 `- ` 之後含「（從……推出）」、且不以「附註：」「[作者裁決]」「例」開頭的行。推導行必須以標籤開頭：`步驟`、`結論` 或 `循環`，接著是由中文數字（〇至十）與「之」組成、不以「之」開頭或結尾的字串，再接全形冒號。標籤全文不重複
- **形-37**：每個「（從……推出）」的內容以 ` + ` 切分，每一項去掉前後空白後須符合以下之一，否則報錯：
  - `前提` 加中文數字，且該前提已列於「前置條件」段落。這一項不符時改報形-23（推導使用的前提未列於「前置條件」），提示文字為程式常數 `PREMISE_UNLISTED`
  - 形-36 格式的標籤，且在本行之前已有一行以這個標籤開頭
  - `概念名 的定義` 或 `UUID.概念名 的定義`（含 `ext:`），概念名在本篇或該上游的概念表中存在
  - 本篇概念名，或上游概念識別
  - `本例效準`，且本行以「例」開頭

  附註只能以「附註：」開頭，沒有標籤，因此不可能成為合法的來源；形-26（附註不作為推導來源）由本條保證
- **形-35（工具部分，警告）**：只看推導行（形-36）。陳述指標籤之後、「（從」之前的文字；以本節的切詞邊界切分，片段恰為本篇概念名者，以及上游概念識別，為陳述用到的概念。所列來源逐項展開成原文：前提與標籤取該行原文（去掉正文引用），加上緊接其後、到下一個條列或段落之前的程式碼區塊內容；「概念名 的定義」與概念本身取概念名與定義全文。陳述用到的概念若在展開後的原文中都沒有出現，列為警告；本篇概念以字面包含比對，原文中出現包含它的較長概念名（例如「信空間」之於「信」）也算出現。陳述含量詞（「每個」「每一」「所有」「任何」「任一」「全部」「恰」「一一」「唯一」，清單為程式常數 `QUANTIFIERS`）而展開後的原文中沒有同一個量詞時，也列入同一條警告。每條警告註明本行之後（略過空行）的第一個非空行是否以「[作者裁決]」開頭：有者標「已有作者裁決（形-35 明文例外）」，沒有者標「無作者裁決，須逐條判斷」。例不檢查。這只是線索：概念沒出現不一定代表來源不足（例如量詞性的「後繼」「時刻」），概念出現也不保證來源足夠，判斷由稽核負責
- **形-38**：以下各行，行尾須有正文引用：「前置條件」段落中的每條前提與限定條件；每條推導行（形-36）；每條以「例」開頭的陳述；「記號約定」「待決項」以外每個段落的「來源：」行。「來源：」行引用的句碼中，至少一個須屬於標題單位
- **跨-30**：正文引用中的每個句碼，都必須是中文論文在 label 執行後的現行句碼之一。報告列出找不到的句碼與引用它的行；這通常表示正文改過，該陳述要重新對照

### 3.6 引用關係（跨-20）

每篇論文的上游集合，取中文論文正文合法連結的目錄去重。從每篇論文出發做深度優先搜尋，回到出發點即為循環，報出完整路徑。外部存根不參與。

### 3.7 報告

validate 結束後，報告讀取 `src/main/resources/` 中的《稽核總表》，從表格列 `| 編號 | 約束 | 檢查者 | 舊編號 |` 取出編號與檢查者：

- 列出英文翻譯尚未開始的論文
- 版本比對略過時（3.9），印出原因與本次未檢查的條目
- 列出檢查者為 AI 與「工具＋AI」的條目，作為 AI 稽核範圍
- 列出檢查者為「作者」與「工具＋作者」的條目，作為作者把關的範圍
- **同步檢查**：本次回報的代碼（含警告）若不在總表中，或總表的檢查者不以「工具」開頭，印出不一致提醒

AI 稽核範圍不寫死在程式裡，一律以總表為準。總表的約束欄與檢查者欄不得含有 `|` 字元，否則解析會錯位。

### 3.8 注釋（論-17、譯-06）

論文檔（中文論文與英文翻譯）讀入時，由 `stripNotes` 處理注釋，產生兩個版本：

- **以空行取代**：注釋的開頭行到結尾行全部換成空行，保留行號。validate 的一切檢查使用此版本
- **整段刪除**：刪除注釋的開頭行到結尾行，連同結尾行之後的一個空行，所以不會留下多餘的空行。輸入包與資料集使用此版本

格式檢查，有任何一項不符即報論-17（中文）或譯-06（英文）：

- 開頭行與結尾行去掉行尾空白後，必須恰好是 `<note>` 與 `</note>`。標籤為程式常數 `NOTE_OPEN`、`NOTE_CLOSE`
- 每個標籤行的前一行與後一行，須為空行或檔案邊界
- 開頭與結尾須成對、不巢狀；只有結尾、或只有開頭而到檔尾都沒有結尾，皆報錯
- 程式碼區塊內出現標籤行，報錯
- 注釋以外的每一行（含程式碼區塊內），以不分大小寫的方式比對 `[<＜]\s*/?\s*note\s*/?\s*[>＞]`，比中者報錯。這是為了抓出寫錯的變體，例如夾在句中的標籤、`<Note>`、`<note/>`、全形的「＜note＞」。比對式為程式常數 `NOTE_RESIDUE`

原始檔中的注釋不被修改。

### 3.10 句碼標籤（論-20）

- 中文論文讀入時，以 `SENT_TAG` 找出所有句碼標籤，記下每個標籤所屬的單位與句碼，然後去掉標籤；形式段單位獨立成行的標籤以空行取代，保留行號。之後的一切檢查使用去掉標籤的版本
- 論-20：依 2.3 節重新切分與計算，檔案中的標籤必須與計算結果完全一致：每個單位恰有一個標籤、位置正確、句碼相同。注釋內、程式碼區塊內、一級標題上出現標籤，或出現以 `<!--` 開頭、含「句」、但不符合 `SENT_TAG` 的註解，皆報論-20
- label 正常執行後，論-20 必然通過。它不通過，通常是 label 因檔案同時有已暫存與未暫存修改而跳過了；報告附上原因

### 3.9 版本比對（概-13、概-19、概-20、概-21、跨-21）

commit 即定稿（說明文件第五節），所以最後一次 commit（`HEAD`）中的概念表就是定稿版。由 `checkHistory` 執行，只讀不寫：

- 以 `git rev-parse --show-toplevel` 找到倉庫，以 `git show HEAD:<路徑>/concepts.md` 取出每個論文資料夾與外部存根在 `HEAD` 中的概念表，用與工作檔案相同的解析器解析
- `HEAD` 中沒有這份概念表時（新論文、新存根），該篇不參與比對
- **概-19**：`HEAD` 中的每個 ID（含已廢棄者）都必須仍存在。改 ID 等於刪一個、加一個，同樣報概-19。概-21（重新生成時舊 ID 都要在）是同一個檢查，報告以概-19 回報
- **概-13**：`HEAD` 中為 `public`、工作檔案中為 `private`
- **概-20（工具部分）**：`HEAD` 中已廢棄、工作檔案中未廢棄。廢棄的 ID 改名後拿去指涉其他概念，工具看不出，由作者把關
- **跨-21**：論文正文連結到的每個上游資料夾（含外部存根），其概念表必須在 `HEAD` 中。只要求上游已經 commit 過，不要求上游沒有未提交的修改：上游勘誤時，下游的配合修改可以在同一次 commit 中完成
- 找不到 git、專案不是 Git 倉庫、或倉庫還沒有任何 commit 時，整段略過，不報不通過；報告印出原因與本次未檢查的條目

基準只用 `HEAD`，不回溯全部歷史：每次 commit 前都會執行 ToolRunner（說明文件 4.9），所以每個 commit 都已經和前一個比對過。

## 四、關係的抽取與分類

### 4.1 目的與格式

從形式化文件中抽取概念之間的關係，寫入 `concepts.jsonl` 每個概念的 `relations` 陣列：

```json
{
  "relation_type": "見 4.2 節九選一",
  "arguments": [
    { "text": "論元原文", "concepts": ["UUID.ID", "……"] }
  ],
  "derived_from": ["推導來源原文", "……"],
  "context": "原始句子",
  "confidence": "high | medium | low"
}
```

- `arguments` 依述詞的論元順序排列。每個論元記錄原文，以及原文中出現的概念。論元可以恰好是一個概念，也可以是由概念構成的陳述，此時 `concepts` 列出其中所有概念
- 概念一律以 `UUID.ID` 識別，本篇與上游概念皆同。形式化文件中寫的是概念名，抽取時以概念表為對照表翻成 ID。概念名可能改動，ID 不會
- `derived_from` 記錄該句「（從……推出）」中列出的來源原文，以 `+` 分隔；沒有推導來源時為空陣列
- 一筆關係會出現在它所涉及的每個本篇概念的 `relations` 中

規則是**決定性的**：同一份輸入，依此規則執行，應得到相同輸出。

### 4.2 relation_type

| relation_type | 對應寫法 | 語意 |
|---|---|---|
| `derives_from` | （從 甲 + 乙 推出） | 該陳述由列出的來源推導而來 |
| `leads_to` | 導致(甲, 乙) | 甲發生會導致乙發生（因果、機制） |
| `conflicts_with` | 衝突(甲, 乙) | 甲與乙不能同時成立（對稱） |
| `mutually_exclusive_with` | 互斥分類(整體, 分支一, 分支二……) | 各分支互斥，且窮盡整體 |
| `implies` | 蘊含(甲, 乙) | 若甲成立，則乙成立 |
| `composed_of` | 組成(整體, 要素一, 要素二……) | 整體由列出的要素構成（不是定義） |
| `narrows` | 收窄(甲, 乙) | 甲是乙的真子集 |
| `member_of` | 屬於(甲, 乙) | 甲屬於乙 |
| `references` | 無 | 純引用，僅提及上游概念 |

程式中的述詞對照表為常數 `PREDICATES`。

### 4.3 抽取範圍

以下內容不抽取：

- 文件頭兩行
- 程式碼區塊內的一切內容。程式碼區塊是論文數學式的摘錄，其中的符號依數學慣例解讀
- 標題行、「來源：」行、以「[作者裁決]」開頭的行、以「附註：」開頭的行。行首的 `- ` 先去掉再判斷
- 各行行尾的正文引用 `【正文：……】`：先去掉，再依 4.4 節處理該行
- 「記號約定」段落與「待決項」段落

其餘的行依 4.4 節處理。

### 4.4 判斷規則

依序執行，命中即停。

**規則 1：述詞。** 句中每個述詞產生一筆關係，`relation_type` 由述詞名稱決定，`confidence` 為 `high`。一句有幾個述詞，就產生幾筆。述詞的論元以括號界定、以半形逗號分隔；論元內可以含有括號，解析時只以最外層的括號與逗號切分。句中同時有推導來源時，寫入每一筆關係的 `derived_from`。

**規則 2：推導來源。** 句中沒有述詞、但有「（從……推出）」時，產生一筆 `derives_from`，`confidence` 為 `high`。唯一的論元是推導來源之前的陳述。「前提五」「步驟三」這類編號照原文記錄，不翻成 ID。

**規則 3：純引用。** 句中沒有述詞、也沒有推導來源，但含有上游概念時，產生一筆 `references`，`confidence` 為 `high`。唯一的論元是整句。

### 4.5 論元中的概念

1. 先取出所有 `UUID.概念名` 或 `ext:UUID.概念名`，以該上游的概念表翻成 `UUID.ID`。找不到時記為 `UUID.概念名(未對應)`
2. 其餘文字以 3.5 節的切詞邊界切分，切出的片段若恰好等於本篇概念表中的中文名，就翻成 `本篇UUID.ID`

複合起點寫成 `導致(甲 與 乙, 丙)` 時，第一個論元的 `concepts` 會同時包含甲與乙。

### 4.6 confidence

`high` 代表**規則命中明確**，不代表語意上保證正確。規則是機械式的比對，形式化文件的述詞用得不精確（例如把因果寫成蘊含）時，規則會忠實反映這個不精確。述詞用法是否精確由稽核把關（稽核總表形-10、形-11）。

依本版規則，所有關係皆為 `high`。`medium` 與 `low` 保留給日後可能加入的非決定性規則。

### 4.7 關係圖的用途

抽取規則是決定性的，關係圖能表達的，形式化文件原文裡都已經寫著，而 `papers.jsonl` 收錄了原文。關係圖對訓練本身沒有增加資訊，它的價值在評測（例如以推導鏈作為標準答案）、自動產生練習題，以及給人閱覽。推導來源中的概念目前只記錄原文、不辨認 ID，需要這些用途時才值得補上。

## 五、bundle

每次執行 ToolRunner，掃描完倉庫後會先刪除所有論文資料夾中的舊輸入包，包括舊版單包 `稽核輸入包.md` 與所有 `稽核輸入包-*.md`。之後以本輪現行材料重建：`形式化輸入包.md` 不以 validate 通過為條件；稽核分包則只有在 validate 全部通過時才產生。validate 不通過時，只重建形式化輸入包，其餘生成物中止，因此不會留下過期的稽核包。

規範文件的目錄為程式常數 `DOCS_DIR = "src/main/resources"`。形式化手冊找不到時，不產生形式化輸入包；稽核總表找不到時，不產生稽核分包。兩者都在報告中寫明缺少的檔案與預期路徑。不產出缺料的包，是為了不讓 AI 在缺少規則的情況下工作。

目前四個現行輸入包都放在論文資料夾中，是生成物：不視為論文檔，不進入資料集，stamp 不處理。建議加進 `.gitignore`：

```
src/main/java/paper_*/形式化輸入包.md
src/main/java/paper_*/稽核輸入包-*.md
```

輸入包中如收錄中文論文或英文翻譯，一律使用注釋整段刪除後的版本（3.8）；中文論文另把句碼標籤改印為可見的【句……】。

### 5.1 上游概念

四個現行輸入包共用同一段「上游概念」：中文論文正文引用到的每個上游條目，含修飾子、中英文名與定義。擷取是**遞移**的：條目定義中又連結到的概念（本篇、上游或存根），一併納入，直到沒有新連結為止。正文與定義中的連結都已在 validate 檢查過（跨-22、概-34），且 public 定義只連 public（概-12），所以擷取到的都是存在、未廢棄的 public 條目。

### 5.2 形式化輸入包

每篇論文都產生 `形式化輸入包.md`，依序包含：

1. 任務說明：不在此列的上游概念一律視為缺失，不得自行推測
2. 形式化手冊全文（讀取 `src/main/resources/群星規範-形式化手冊.md`）
3. 上游概念
4. 本篇概念表全文
5. 本篇中文論文全文（注釋已刪除）。每個句碼標籤改印為可見的【句……】，位置不變，供形式化引用

### 5.3 稽核輸入包

四個產物都完成時，bundle 依《稽核總表》0.3 的「稽核包／AI 條目」表產生全部稽核分包；目前為 `稽核輸入包-甲.md`、`稽核輸入包-乙.md`、`稽核輸入包-形35.md`。形式化文件須在「記號約定」「待決項」之外至少有一個段落，英文翻譯也須已開始（3.2 節）；validate 已通過，所以兩個待決項區塊必為「無」。條件不滿足時，所有稽核分包都不產生，報告印出略過原因。

分工**不在 Java 另寫一份條目清單**。`loadAuditPackages` 直接讀稽核總表 0.3；產包前以 `auditPackageProblems` 驗證：全部分包必須把總表中全部「AI」與「工具＋AI」條目恰好分完，各包不得重複、不得包含非 AI 條目，而且每包皆不得為空。任何一項不成立時，所有稽核分包都不產生並在主控台報錯。日後移動條目，只改稽核總表即可。輸出檔名直接使用分包名：`稽核輸入包-<稽核包>.md`。

各包都依以下結構產生：

1. **A. 稽核規範**：稽核總表全文（讀取 `src/main/resources/群星規範-稽核總表.md`）。
2. **B. 本包範圍與已完成的工具檢查**：聲明 validate 全部通過；依 0.3 分包表只列本包的 AI／工具＋AI 條目；工具警告也只收入代碼屬於本包者。標 `*` 的條目表示「工具＋AI」，AI 只檢查工具未涵蓋的語意部分。
3. **C. 參照資料**：5.1 節的上游概念。
4. **D. 被稽核資料**：本篇材料全文。所有包都包含中文論文、`concepts.md`、`formalization.md`；分到跨-16 或跨-17（以及日後若有 AI 稽核的 `譯-*` 條目）的包才另外包含英文翻譯。中文論文中的句碼標籤改印為可見的【句……】。
5. **E. 推導檢查材料**：依文件順序，每條推導（形-36）與每條例一節，包含：
   - 標籤與陳述原文
   - 來源逐項展開：前提取「前置條件」中的全文；標籤取該行陳述原文；「的定義」與概念本身取定義全文，本篇取概念表，上游取 5.1 節的條目
   - 本行正文引用的原句，附句碼與所在章節的標題；第一個標題之前的單位標為「篇首」
   - 同一段落中緊接在本行之後的 `[作者裁決]`

分到跨-10、跨-11 或跨-13 的包再加：

6. **F. 未被引用的正文單位**：形式化文件的正文引用中從未出現的單位，依文件順序列出句碼與原文；標題單位列在最前面，另成一組。這一區供推導完整性檢查使用。

目前因此只有甲包收 F 區；乙包與形35 包不收。英文翻譯目前只有乙包需要；甲包與形35 包不收。三包都保留 E 區：甲包用於推導對照，乙包的跨-31 需要逐處核對形式化／正文，形35 包則逐條檢查來源是否足以推出結論。這使形-35 雖然獨立成包，但不再攜帶與它無關的英文全文與未引用正文清單。

## 六、資料集

- `concepts.jsonl`：每行一個本篇概念，欄位 `id`（`UUID.ID`）、`concept`、`concept_en`、`modifier`、`paper_uuid`、`paper_title`、`definition`、`definition_source`（第一筆相關關係所在的段落標題）、`deprecated`、`relations`。外部存根不輸出

- `HF_DATASET` 記錄要檢查的 HF 資料集。尚未發布時留空，第 8 步略過

## 八、執行環境

- 需要 Java 21 以上
- 在 Linux 上執行時要設定 UTF-8 語系（例如 `LC_ALL=C.UTF-8`），否則讀到中文檔名會中斷
- stamp、label 的重新暫存與版本比對需要 git。找不到時 stamp 與版本比對略過；label 照常寫入，但不重新暫存
