## 一、為什麼需要這套東西

### 問題

框架有十幾篇互相引用的論文，而且還在演化。改了一個概念的定義，哪些下游論文的引用斷了？靠人腦記不住。漏了就是內部矛盾，而且不會立刻發現。

### 方案

每篇論文產出一份**概念表**，登記本篇定義的所有概念。論文正文中的每個概念都是一個指向概念表條目的超連結。檢查腳本掃描全部連結，連不上的就報錯。

概念表是論文唯一的對外介面，而其中只有標為 `public` 的條目可以被下游引用。

### 為什麼不是型別系統或其他工具

前身規範把概念翻譯成 Java record，靠編譯器偵測引用斷裂。實測下來，它唯一的功能是「確認本篇概念仍連著原本的上游」，而這件事連結檢查腳本做得更完整：Java 的每個 record 至多追蹤一個上游，腳本能檢查正文裡的每一個引用，而且在論文寫完的當下就能跑，不必等翻譯成 Java。既然有更低成本的做法，Java 層整個移除。

OWL、Lean、Prolog 之類的工具，解決的是「從已知推未知」或「嚴格證明」的問題。本框架要解決的是「改了舊的，哪裡斷了」，這是不同的問題，用它們是殺雞用牛刀。

邏輯自洽性和自然語言分析交給 AI，AI 直接讀中文論文，概念表也由 AI 產出。腳本只做 AI 做不好的事：機械、重複、不能漏的連結追蹤與格式檢查。**腳本只驗收，不生產。**

### 四層分工

| 層 | 功能 | 載體 | 做什麼 | 做不到什麼 |
|---|---|---|---|---|
| 論文 | source of truth | `中文標題.md` | 承載完整論證：定義、推理、證據、邊界。正文給 AI，注釋給作者，同在一檔 | 有歧義，不報錯，改了不通知 |
| 概念表 | 對外介面 | `concepts.md` | 登記本篇概念，public 條目供下游引用；定義用自然語言 | 是有損壓縮，不含論證過程 |
| 形式化 | 自洽性檢查 | `formalization.md` | 攤開論證結構，供多 AI 逐條稽核 | 不表達定義，不供下游閱讀 |
| 檢查腳本 | 機械檢查 | `ToolRunner.java` | 連結斷裂、格式違規，一個都不漏 | 只查存在性與格式，不查語意 |

### 三條核心原則

**一、幾何學式引用。** 下游只能使用上游的**概念**，不能引用上游的**論證**。一篇論文引用另一篇時，引用的必然是某個具體概念；不存在「參見某篇第三節」這種不經由概念的引用。

因此，引用只能經由概念表的 `public` 條目，沒有例外。框架內不存在可跨論文引用的公設編號、原語或其他構件。論文內部當然可以有公設、前提、步驟的編號，但它們只是本篇的局部標籤，不能被其他論文引用。

**二、概念的身分是 `UUID + ID`。** UUID 標示論文，ID 標示該論文內的概念。顯示名稱不是身分的一部分，所以：

- **只改名字**（修錯字、換個更貼切的說法）：ID 不變，下游不受影響。
- **改了語意、需要通知下游**：廢棄舊 ID，另開新 ID，所有對舊 ID 的引用立刻報錯。

前身規範把這兩件事綁在一起，想修個錯字也得讓全部下游崩潰。分開之後，要不要驚動下游由作者決定。

**三、public 與 private。** 論文的每個結論都依賴本篇的前提，所以「是否依賴前提」不能拿來決定一個概念能否公開。本框架採用數學論文的做法：

- `public` 條目是對外介面，只有三種：**通用的定義**，指向一類東西，下游可以代入自己的對象使用；**自己標明適用範圍的結論**，下游引用時範圍隨之帶入；**鐵律**，框架承認、不由其他條件推出的律，所有下游的模型都必須滿足。
- `private` 條目是本篇特有的構造與局部記號，相當於數學論文中「本文中記某某為……」。下游不得引用，但可以在自己的前提下定義同名的概念。

同一個名稱在不同前提下可能得到完全不同的結果：無重力前提下的「掉落」，物體停在原處；地表前提下的「掉落」，加速度為九點八。這正是 private 存在的理由。

public 定義只能連結 public 條目。下游引用一個 public 概念時，它的定義用到的每個詞也都能直接引用，不必重新解釋；這是為了避免同一個詞在下游被一再重建。private 可以隨時改為 public；public 改為 private 會使既有的下游引用失效，定稿後禁止。

### 一句話邊界

**檢查腳本是一本會自動報錯的概念登記簿，不是邏輯引擎、不是推理系統、不是知識圖譜。**

### 危險與邊界

論文是否邏輯自洽，最終由多 AI 稽核判定。這裡有一個無法消除的風險：所有 AI 的訓練數據高度重疊，偏差方向可能相關。如果錯誤落在共同盲區，多 AI 會一致放過。

定稿條件綁在稽核結果上（見第五節），所以這個風險不只是檢查品質問題，而是定稿標準問題。緩解辦法有兩個：一是要求稽核報告列出實際查到的證據，例如「跨-14 通過，檢查了以下 13 條前提」，而不是只回報「通過」；二是能機械判定的約束一律交給腳本，不交給 AI，讓 AI 的注意力集中在真正需要語意判斷的地方。

形式化的價值在於提高下界，不在於消除盲區。

## 二、倉庫結構

所有論文存放在同一個 Git 倉庫的 `src/main/java/` 之下。沿用 Maven 目錄結構，是為了讓 `ToolRunner` 能在同一個專案裡編譯執行，也為將來可能新增的程式層預留位置。Maven 編譯只處理 `.java` 檔，資料夾裡的 `.md` 不受影響。

資料夾名稱使用 `paper_` 前綴加上 UUID（`-` 替換為 `_`）。每個論文資料夾內含固定四個檔案：

```
[倉庫根目錄]
  ├── src/main/resources/                 （規範文件，ToolRunner 從這裡讀取）
  │     ├── 群星規範-說明文件.md
  │     ├── 群星規範-論文手冊.md
  │     ├── 群星規範-概念表手冊.md
  │     ├── 群星規範-形式化手冊.md         （附在形式化輸入包中）
  │     ├── 群星規範-稽核總表.md           （附在稽核輸入包中；報告讀取「檢查者」欄）
  │     └── 群星規範-工具規格.md
  ├── src/main/java/
  │     ├── paper_54c0291d_05b3_431a_9f2a_1b8ec93c3c3f/
  │     │     ├── 中文標題.md            （論文，正本）
  │     │     ├── English Title.md       （英文翻譯）
  │     │     ├── concepts.md            （概念表，對外介面）
  │     │     ├── formalization.md       （形式化文件，內部稽核用）
  │     │     ├── 形式化輸入包.md        （生成物，用完可刪）
  │     │     └── 稽核輸入包.md          （生成物，用完可刪）
  │     ├── paper_……/
  │     ├── ext/                          （外部來源存根）
  │     │     └── ext_aaaaaaaa_bbbb_4ccc_8ddd_000000000000/
  │     │           └── concepts.md       （只有概念表）
  │     └── tools/
  │           ├── ToolRunner.java         （檢查、時間戳、匯出）
  │           └── NewPaper.java           （建立新論文，共用 ToolRunner 的程式碼）
  └── exports/                            （資料集輸出，生成物）
```

規範文件放在 `src/main/resources/`，是 Maven 放非程式檔的標準位置。ToolRunner 從這裡讀取形式化手冊與稽核總表，找不到時不產生對應的輸入包，以免 AI 拿到缺少規則的輸入。檔名必須一字不差；下載時被加上前綴或編號的檔案要先改名。

沒有任何一篇論文享有特殊地位。引用關係構成任意 DAG，不要求收斂到單一根節點。新論文可以引用任何既有論文，也可以完全不引用、從零開始。

### 外部存根

外部存根記錄詮釋者對**非本倉庫來源**的概念理解：書籍、資料庫、官方統計，或活在另一個倉庫的論文。存根不走形式化與稽核流程，只有一份概念表。格式見概念表手冊第九節。

外部存根只用於引用外部資料，或需要特別標註的專業術語。標準數學用語（加法、張量積、等距映射、偏跡等）視為一般用語，不建存根。否則連加法都要建存根，框架無法運作。

外部存根位於 `ext/` 之下，比論文資料夾多一層，因此連結路徑有兩種形式。這是為了維持既有結構不動，代價是腳本的正規表達式要多寫一種情況。

## 三、概念身分與生命週期

### ID 規則

ID 在單篇論文內唯一，全域識別用 `UUID + ID`，格式為 `c` 加流水號。**定稿後，ID 永不修改、永不重複使用。** 概念廢棄後，它的 ID 也一併作廢，不得再分配給新概念，否則舊的下游引用會悄悄指向另一個概念，這是整套機制裡最危險的失效方式。

廢棄的條目保留在概念表中並標記為已廢棄，不得直接刪除。這樣腳本才知道哪些 ID 曾經用過，也才能在下游引用到廢棄概念時回報「已廢棄」而不是「找不到」。這兩者對下游作者的意義完全不同。

### 定稿前後

定稿（commit，見第五節）之前，論文不會被任何人引用，ID 怎麼調整都沒有影響。定稿之後，概念表只能增量修改。

如果概念表由 AI 重新生成，必須參考舊版，不得重新編號。ToolRunner 會拿工作中的概念表和最後一次 commit 比對：舊 ID 消失、`public` 改為 `private`、已廢棄的條目恢復使用，都會報錯（工具規格 3.9）。工具看不出的只有一種情形：把廢棄的 ID 改個名字，拿去指涉另一個概念。這一部分仍由作者把關。

### 連結格式為什麼卡死

正文中每個概念都是真正可點擊的 Markdown 相對連結，只允許三種形式（論文手冊 1.5 節）。格式卡死有兩個理由：一是讓腳本不會漏判，一旦允許多種寫法，就會有漏網的引用而作者不會察覺；二是相對路徑同時編碼了論文的位置，讀者可直接點開，AI 也能據此定位上游檔案。本規範不使用遠端路徑拼接，也不設 base_url，連結在本地和 GitHub 網頁上都能直接點開。

程式碼區塊裡的連結不會生效，所以程式碼區塊內不標注；作為交換，每個概念至少要在程式碼區塊外被連結一次。

### 顯示名稱為什麼自由

方括號裡的顯示文字由作者自由決定，不必等於概念表裡的名稱。甲論文和乙論文都可能有一個叫「刺激」的概念，丙論文同時用到兩者時，必須能寫成「感官刺激」和「語意刺激」以區分。作為交換，腳本檢查反方向的錯誤：同一篇論文內，同一個顯示文字不得指向兩個不同的 ID。

英文版的顯示名稱受概念表英文名約束，自由度較小；兩個概念英文名相同時，以限定詞區分（論文手冊 2.4 節）。

## 四、流程

```
草稿（暫存資料夾，或已由 NewPaper 建立的資料夾）
   ↓
【論文手冊・任務一】   AI 協助撰寫正文、替換標題
   ↓ 作者定稿正文；以 NewPaper 建立的資料夾放進正式位置（從此進入稽核流程）
【概念表手冊】         AI 產出概念表、分配 ID、回填正文連結 → 概念層待決項
   ↓ ToolRunner 產出形式化輸入包
【形式化手冊】         AI 讀形式化輸入包，產出形式化文件 → 論證層待決項
   ↓
【論文手冊・任務二】   AI 產出英文翻譯
   ↓ ToolRunner 產出稽核輸入包
【稽核總表】           至少兩個獨立 AI，各拿一份稽核輸入包逐條稽核
   ↓ 裁判判定
commit（即定稿）
```

每個生產階段只給 AI 一份手冊；稽核只給稽核總表。生產手冊寫「怎麼做」，稽核總表寫「必須成立什麼」。

### 4.1 論文註冊

執行 `tools/NewPaper.java`，不需要任何輸入。它會生成 UUID（v4），在 `src/main/java/` 之下建立 `paper_UUID` 資料夾，並從模板建立四個檔案。資料夾名稱從此不可更改。

執行的時機有兩種：

- **草稿寫好之後**（通常的做法）：草稿先在倉庫以外的暫存資料夾中撰寫，確定要進入檢驗流程時才執行 NewPaper，把內容貼進模板。
- **一開始就執行**：直接在正式資料夾中撰寫。

資料夾一旦在 `src/main/java/` 之下，ToolRunner 每次都會掃描它。草稿階段的 validate 必然有不通過（佔位符、標題等），而 validate 不通過會中止整個 ToolRunner，連其他論文的輸入包也不會產生。所以除非這段期間不需要執行 ToolRunner，草稿以放在暫存資料夾為宜。

兩個論文檔名是標題佔位符 `中文標題.md` 與 `English Title.md`。標題屬於語意判斷，由 AI 在撰寫過程中替換；NewPaper 只負責機械的部分。佔位符忘了替換，validate 會以論-04、譯-01 攔下；只改了其中一部分，會以論-05、譯-02、跨-29 攔下。

中文標題可以後改；英文標題決定後不再更動。英文標題沒有被任何連結或 ID 依賴（連結都指向 `concepts.md`），所以它在什麼時候決定，不影響任何機制。標題中不放版本號，版本由 Git 追蹤。

新論文一律由 NewPaper 建立，不要複製舊論文的資料夾。前身規範的論文資料夾裡有 Java 程式碼，複製過來的殘留檔案會造成編譯錯誤。

### 4.2 寫論文

給 AI 論文手冊，執行任務一。寫作期間 ID 尚未定案，概念在定義處以佔位符 `#new` 標注，這段期間 validate 會一直回報佔位符，這是預期的。

**論文是中文。** 正文、標題與程式碼區塊都不使用拉丁或希臘字母。單字母變數降低可讀性，而且會讓概念表的中文名與論文的符號對不上。允許的外文以六角括號 `〔〕` 標記，腳本據此判斷哪些外文是允許的例外。

**正文與注釋。** 論文的讀者主要是 AI：概念表、形式化、稽核、下游論文都從它出發。這種文字必須精確、用詞固定，讀起來不像給人看的。與其讓正文兩頭遷就，不如讓它徹底為 AI 而寫，再為每段附上白話注釋給作者自己看（論文手冊 1.9 節）。注釋和正文放在同一個檔案裡，改正文時一眼就看得到；不另設一份人話檔案，免得多一份要維護的文件。工具在一切檢查與打包之前刪除注釋，所以注釋不會汙染 AI 的材料，作者當時的意思也不會丟。人話隨正文一起寫、一起改，一致性在產生的時候就保證了，不另設稽核條目。

**上游記號。** 上游論文的正文與形式段對下游不可見，下游的形式段若需要上游概念的記號，只能自己寫一份。規則見論文手冊 1.10 節：記號段前要有固定句，記號只能依上游概念表的定義寫出。形式化文件不摘錄這類記號段，免得被當成複製上游定義（稽核總表跨-26）。

### 4.3 產出概念表 → 概念層待決項閘門

給 AI 概念表手冊與上游概念表。辨認概念、判斷粒度、分配 ID、撰寫定義、取英文名、回填正文連結，全部是語意判斷，機械規則做不了。

登記的原則是**能分辨就分辨**；判準是「是否被命名與定義」，不是「是否可能被引用」。

這一階段要由作者裁決的是**介面層面**的問題：概念粒度、是否為獨立概念、封閉分類是否窮盡、與上游某概念是不是同一個東西，以及每個條目的修飾子。修飾子可以請 AI 做成一張建議表，一次裁決。

裁決為不登記的構件，記錄在「不登記」區塊，否則下次重新生成概念表時，AI 會再把它當成未登記的構件抓出來。

這些必須清零才能進入下一步。

### 4.4 連結檢查與打包

執行 ToolRunner。validate 全部通過後，bundle 會在論文資料夾中產出 `形式化輸入包.md`：形式化手冊全文、所有被引用到的上游概念條目（遞移擷取）、本篇概念表、本篇論文正文（注釋已刪除）。

這時英文翻譯還沒做，英文檔仍是模板。validate 把原封未動的模板視為「尚未開始翻譯」，暫不檢查「譯」組與跨-19，所以不會擋住這一步。

輸入包放在論文資料夾裡，是為了好找。它們是生成物：每次執行 ToolRunner 都會先刪掉舊的再重建，validate 沒過就不會留下；用完可以直接刪。建議加進 `.gitignore`（見工具規格第五節），免得被誤 commit。

輸入包開頭聲明「不在此列者一律視為缺失，不得自行推測」，以堵住 AI 缺料時腦補定義。它看到「刺激」兩個字，不一定會說自己缺資料。

### 4.5 形式化 → 論證層待決項閘門

把 `形式化輸入包.md` 交給 AI。輸入包裡已經附上形式化手冊，不必另外給。

形式化的產物實質上是**判決**，不是給人讀的文件。它要回答的問題只有一個：這篇論文邏輯自洽嗎？那份 `.md` 存在的理由是「不攤開就沒辦法逐條檢查」，不是「有人要讀它」。因此它不對下游開放，也不需要遷就閱讀體驗。

形式化文件的寫法有幾項設計決策：

- **關係用中文述詞，不用符號。** 例如 `組成(宇宙空間, 信空間, 環境總空間)`，而不是 `宇宙空間 ≡ 信空間 ⊗ 環境總空間`。這是邏輯學的慣例：符號只留給最少的邏輯骨架，領域關係一律取名字。符號數量有限，同一個符號在不同領域意思不同（例如 `⊗` 在數學中是張量積），形近的符號又容易混用；述詞則讓抽取工具直接讀出關係類型與兩端。
- **概念名以空格分隔。** 中文沒有空格，概念名又常互相包含（「信」與「信空間」），不分隔就無法機械地切詞。論文與概念表以連結的方括號界定概念，形式化文件沒有連結，所以改用空格。
- **每條陳述都有角色**：前提、限定條件、推導、附註、例、效準。社會科學論文的論證藏在文字裡，形式化要把隱含的邏輯挖出來；數學論文正好相反，證明已經寫好，會出問題的反而是文字的部分：宣告了卻沒用到的前提、沒宣告的前提、擋誤讀的修辭句、論文對自身的描述。限定條件、附註、例這幾種角色，就是讓這些東西有明確的位置。
- **現實案例是效準，不是證明。** 抗藥性、日心說這類案例裡的經驗事實，本來就不由四條律推出；要求推出它們，等於把理論倒過來。所以經驗事實標為效準，不需要來源；用框架去讀它所得的陳述標為例，仍要符合定義。效準只在自己的段落裡當例的來源，不回流成本篇的推導。
- **前提的寫法固定**為 `- 前提一：……`，因為工具要據此檢查每條前提是否被引用過。

這一階段要裁決的是**論證層面**的問題：推導跳步、前提缺失、可證偽條件對不上、機制環節不明。作者裁決時只需要判斷「這個敘述在邏輯上對不對」。形式化文件是 AI 產出的，符號、格式這類細節不需要作者回想當初的意圖。

### 4.6 英文翻譯

給 AI 論文手冊，執行任務二，附上本篇與上游概念表。放在形式化之後，是因為形式化的待決項可能導致論文修改，先翻會重翻。

翻譯時，所有概念的英文顯示名稱以概念表的英文名為準，可做詞形變化但不得另譯。這保證同一個概念在不同論文的英文版裡譯名一致。中文沒有詞形變化，逐字相同與語意相同是同一件事；英文則必須區分詞形變化與另譯。

注釋也一併翻譯。英文讀者看不懂任何一份中文檔案，英文版是唯一的入口；稽核時，中英兩份都先由工具刪除注釋，再照原本的規則比對。

### 4.7 多 AI 稽核

先執行 ToolRunner，全部通過。四個產物都完成時，bundle 會在論文資料夾中產出 `稽核輸入包.md`：稽核總表全文、工具檢查結果與本篇警告、上游概念、本篇四個檔案全文（中英文論文的注釋已刪除）。形式化或英文翻譯還沒做完時，報告會說明略過的原因。

把 `稽核輸入包.md` 分別交給至少兩個獨立 AI。指令不必寫長，總表本身就是指令，例如：「依稽核總表第零節，稽核這篇論文，逐條輸出編號、判定與實際查到的證據。」

操作上要注意：

- **獨立性要靠作者保證。** 兩個 AI 要在不同的對話中進行，不共享上下文。產出任何一份產物的 AI，不適合擔任稽核者。
- **稽核只給稽核輸入包，不給生產手冊。** 總表的第八節已收錄判斷所需的定義。多給手冊只會讓 AI 在兩套措辭之間猶豫。
- 稽核報告交給裁判（另一個 AI），逐條判定是否成立，屬於實質或形式；兩份報告判定不一致時，也由裁判判定。細節見稽核總表 0.8、0.9。

### 4.8 裁決規則

**所有待決項一律由作者親自裁決。** AI 不得自行清除待決項，也不得因為作者未回應就採用「暫定處理方式」繼續往下做。概念粒度、封閉分類是否窮盡這類問題，AI 不該代替作者決定。

概念層的裁決記錄在概念表的對應條目之下，不登記的裁決記錄在「不登記」區塊；論證層的裁決以 `[作者裁決] 理由` 記錄在形式化文件的對應位置。前身規範把所有結論都記在形式化文件裡，而那份文件沒有讀者，等於把概念層的裁決埋掉了。

如果同一類問題反覆出現並反覆卡住，通常不是個案，而是框架本身有東西沒定義清楚，應該回頭檢查手冊是否缺了某種構件。

### 4.9 提交

1. **確認已滿足定稿條件**（稽核總表 0.9）。commit 即定稿，條件未滿足前不 commit。勘誤則要先完成稽核總表 0.7 的修正與重新稽核。
2. **檢查改動**，把這次要提交的檔案加入 Git 暫存區。要提交哪些檔案，由作者決定。
3. **執行 ToolRunner。** 第 0 步會把暫存檔案的時間戳更新為當下時間並重新暫存，接著執行 validate；validate 也會拿工作中的概念表和最後一次 commit 比對（工具規格 3.9）。
4. **validate 通過後 commit**，寫下提交說明。若修改是在與 AI 的對話中完成的，可以請 AI 擬提交說明的草稿，理由由作者確認。
5. **手動 push。**

四個檔案一起 commit。UUID 不變，Git commit history 即 changelog。

暫存之後若又修改了同一個檔案，要重新暫存再執行 ToolRunner。同時有已暫存與未暫存修改的檔案，第 0 步會跳過並提醒，以免把刻意不提交的修改一併暫存。

每次 commit 前都執行 ToolRunner，這一點也是版本比對成立的前提：每個 commit 都已經和前一個比對過，所以只拿最後一次 commit 當基準就夠了。

**Git push 一律由人類手動執行，任何管道嚴禁自動 push。**

## 五、定稿判準

一篇論文必須同時滿足以下三項，才可以 commit：

1. validate 全部通過。
2. 兩道待決項閘門都已清零（都由作者親自裁決）。
3. 最近一輪稽核經裁判確認沒有成立的實質問題，成立的形式問題都已修正，作者選擇項都已裁決。

**commit 即定稿。** 稽核通過、裁判確認之前不 commit；commit 之後，該論文四個檔案的任何修改都屬於勘誤，依稽核總表 0.7 處理。定稿狀態因此不需要另外記錄：最後一次 commit 中的版本就是定稿版，可以被下游引用；定稿之後，ID 凍結（見第三節）。

這個做法成立，是因為作者一次只寫一篇論文：草稿在暫存資料夾中寫，放進正式資料夾後走完檢驗流程才 commit，所以倉庫裡不會出現未定稿的論文被引用的情況。這和寫程式一樣：你不會假設自己引用的其他物件是個未成品。

定稿既然等於 commit，依賴定稿狀態或版本歷史的條目，工具就能拿工作中的檔案和最後一次 commit 比對（工具規格 3.9）。只有工具看不出的部分，才由作者把關。

這不是高標準，是能不能用的分界線。本框架的論文是幾何學式的推論演繹，不自洽不是品質瑕疵，而是根本不成立：下游接上去，繼承的是假前提，從假前提什麼都推得出來，整棵樹就廢了。就像編譯不過的程式碼不是程式，只是一堆文字。

因此，稽核不通過時正確的反應是修改或重寫，不是把問題壓下去繼續往上蓋。

## 六、工具

所有例行工具合併為單一檔案 `tools/ToolRunner.java`，在 IDE 中執行 `main` 即依序跑完第 0 到第 8 步。建立新論文會新增原始檔，性質和例行檢查不同，另外放在 `tools/NewPaper.java`，直接呼叫 ToolRunner 的程式碼，不重複實作。合併的理由是這些功能共用同一批解析邏輯（YAML 頭部、概念表、正文連結、UUID 與 ID），拆成多檔會讓同一段程式散落各處，格式變動時改不齊。

各步驟的職責、validate 的檢查方式、關係的抽取與分類，見《工具規格》。

**stamp 是唯一會修改原始檔的步驟**，也是「腳本只驗收，不生產」的唯一例外。它只改時間戳那一行，而且只改 Git 暫存區中的檔案；沒有暫存任何檔案時什麼都不做，所以每次執行都無害。

**validate 有「不通過」即中止**，不執行後續步驟：格式沒過就匯出，等於在處理有問題的資料。「警告」不阻擋流程，但要人工確認，例如正文中字面上等於概念名卻沒加連結的片段，腳本無法判斷它是否在指涉那個概念。

**版本比對內建於 validate。** validate 讀取最後一次 commit 中的概念表，和工作中的檔案比對，只讀不寫。找不到 git 或倉庫還沒有任何 commit 時略過，報告註明哪幾條本次未檢查。

**關係的抽取與分類內建於第 5 步。** 改用中文述詞之後，規則完全是機械式的，不需要另外交給 AI 分類。

**注釋在讀檔時就刪除。** 論文檔一讀進來，注釋就被處理掉，之後的檢查、打包、匯出都只看到正文；原始檔中的注釋不被修改。這和編譯器不編譯註解是同一回事。

**資料集名稱：** ToolRunner 開頭的常數 `HF_DATASET` 記錄要檢查的 HF 資料集。新專案尚未發布資料集，這個常數目前留空，第 8 步因此略過；發布後把名稱填入即可恢復。

## 七、檢查分工

每條約束由誰檢查，記在稽核總表的「檢查者」欄：

| 檢查者 | 意思 |
|---|---|
| 工具 | ToolRunner 的 validate 檢查，一個都不漏 |
| AI | 需要語意判斷，由多 AI 稽核逐條檢查並附證據 |
| 工具＋AI | 工具查機械的部分（例如固定字眼、字面比對），AI 查其餘 |
| 工具＋作者 | 工具查機械的部分（例如與最後一次 commit 比對），其餘工具與 AI 都看不到，由作者把關 |
| 作者 | 工具與 AI 都無從得知的事，例如待決項是否由作者親自裁決，由作者的工作紀律保證 |

ToolRunner 的報告直接讀取這一欄列出 AI 稽核範圍，不另外寫死一份清單；工具回報的代碼若在總表中找不到、或檢查者不以「工具」開頭，報告會提醒。

**腳本只查存在性與格式，語意正確性靠 AI 讀論文與概念表。**

## 八、文件清單

| 文件 | 讀者 | 什麼時候給 |
|---|---|---|
| 論文手冊 | 撰寫論文、翻譯的 AI | 任務一（撰寫）、任務二（英文翻譯） |
| 概念表手冊 | 產出概念表的 AI | 產出概念表、依裁決修改 |
| 形式化手冊 | 形式化的 AI | 已附在形式化輸入包中，不必另給 |
| 稽核總表 | 稽核 AI | 已附在稽核輸入包中，不必另給；也是全部約束的正本 |
| 工具規格 | 作者、修改工具的 AI | 修改 ToolRunner 或 NewPaper 時 |
| 說明文件 | 作者 | 不進入 AI 任務（本文件） |

**生產手冊是稽核總表的抄本。** 同一條規則在總表與手冊中各寫一次：總表寫「必須成立什麼」，手冊寫「怎麼做」。兩者不一致時以總表為準。約束編號只存在於總表，手冊只在需要時註明「對應總表某條」。

每份文件只標記最後修改時間戳（精確至秒，格式 `YYYY-MM-DDTHH:MM:SS`），由 stamp 更新，不使用遞增版本號。這些時間戳只供作者對照，沒有任何檢查依賴它。

手冊改動後，既有論文的產物不會被自動標記為過期。下一次稽核時，稽核 AI 拿當前的總表檢查全部檔案，不符合新規則的地方會在那時被抓出來。

## 九、版本管理

- 論文是正本。
- 概念表、形式化文件、英文翻譯都是生成產物，不手動維護（裁決記錄除外）。
- 論文修改後重新執行 4.3 之後的全部步驟。
- 四個檔案一起 commit，Git commit history 即 changelog。commit 即定稿（第五節）。
- 概念語意變化時，依第三節的規則決定是保留 ID 還是另開新 ID；若另開新 ID，下游的引用會在連結檢查中報錯，由作者決定處理方式，在同一次 commit 中完成。
- 修改任何一份規範文件或工具時，六份文件與兩支 Java 必須一起放進同一次對話，並在修改結束前確認彼此一致。

最後一條取代了「由程式檢查手冊與工具是否一致」的做法（唯一的例外是報告對稽核總表「檢查者」欄的同步提醒，因為它讀的本來就是同一份資料）。作者只有一個人，每次修改時所有東西本來就放在一起處理，一致性由修改的過程保證，比事後用程式檢查便宜得多。但這個前提只在「所有文件都在同一個上下文裡」時成立。檔案若是陸續提供，AI 會在看不到其他文件的情況下修改，工具與手冊就會開始不一致。對話很長時，早期讀過的內容也可能被擠出上下文，修改結束前應重新讀取一次全部文件再確認。需要同步檢討的對應關係，見工具規格第七節。
